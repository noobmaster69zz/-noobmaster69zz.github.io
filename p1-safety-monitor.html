01 — Project scope & client's problem

A supervisor cannot watch every worker at once.

Falls, slips and trips are among the most common causes of injury on construction sites. Workers operate at height, cross uneven ground and carry equipment, and when something goes wrong there is often nobody watching. An incident can go unnoticed for minutes.

Our team of four was asked to build a wearable prototype that continuously monitors movement and raises an alert when a possible incident occurs. The scope covered the full data engineering pipeline — collection, transmission, validation, processing, storage, retrieval and visualisation — for a single device paired to a nearby computer. GPS tracking, cloud deployment, medical diagnosis and automatic emergency notification were explicitly out of scope.

02 — My role & solution

I owned everything downstream of the sensor: storage, retrieval and the screen.

My teammates handled the firmware, the BLE client and the detection algorithm. My responsibility was database, dashboard and visualisation — turning a 100 Hz stream into something durable, and then into something a supervisor could read at a glance.

The schema was the first real decision. Rather than one wide table, I split the pipeline across three, so the raw record is never overwritten by processing. That means thresholds can be re-tuned and an entire recorded session replayed without collecting a single new sample.

nesso_db — the schema I designed. Tap a table.

Two backends behind one interface. I wrote a DataStore class that hides the difference between MariaDB and SQLite — the SQL is nearly identical and only the parameter placeholder differs, so the rest of the project doesn't care which is running. MariaDB is the real server; SQLite is a zero-setup fallback that keeps a demonstration alive if the server won't start. Switching is one line in config.py.

Writes are buffered, not per-sample. At 100 Hz, committing every reading individually would mean 100 transactions per second. I buffer samples and flush every 100, cutting database round-trips by two orders of magnitude while keeping at most one second of data at risk.

The dashboard states its verdict before its data. A red banner names the active alert with type, severity, peak value and timestamp; a green banner confirms all clear. Below sit four metrics, live acceleration and angular-rate charts, and the full event log — refreshing every three seconds without anyone touching the database directly.

04 — Outcome & results achieved

A working monitor — and a defect the dashboard exposed.

The system ran end to end. Motion data streamed from the Nesso N1 over BLE, was validated, stored and analysed, and surfaced live. In the recorded demonstration the pipeline logged 3 falls or slip-trip-falls and 5 near misses, each stored with type, severity, peak value and timestamp, with the most recent shown in the banner.

The finding

A threshold that could never fire.

Plotting angular rate next to the configured near-miss threshold showed something wrong. The recorded gyroscope values peak around 0.18, while NEARMISS_GYR is set to 350 deg/s. Those two numbers cannot both be right — the rotational branch of the detector is mathematically unreachable, meaning every near miss in the demonstration was raised by the post-impact recovery path instead.

The likely cause is a units or scaling mismatch between the firmware and the configured limits. It is not a bug any single component would reveal on its own: the firmware transmits, the detector runs, the database stores and the dashboard draws — every part reports success. It only becomes visible when the visualisation is read against the configuration, which is exactly what the dashboard layer is for.

Limitations & what I would improve

The sample counter is a display cap, not a total. The dashboard queries the most recent 1000 rows, so the "samples stored" metric reads 1000 once that many exist, regardless of how much data is held. It should read a COUNT(*) from the database rather than the length of a limited result set.

No accuracy figures are reported, deliberately. We had no labelled movement dataset, so precision, recall and false-positive rates cannot be calculated honestly. Quoting a detection rate from a handful of staged tests would be a number without meaning. Measuring properly needs labelled data from multiple users and movement styles.

Other constraints. The system supports one device with no worker or session identity, so it cannot scale to a site. Everything runs locally — a real deployment would need a cloud database and push notifications rather than an on-screen banner. Detection thresholds are fixed rules rather than a learned model.
